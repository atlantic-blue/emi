# The contracts version 1 must satisfy

A contract says what one part of Emi must do. It states the input, the output and every error that
part must produce. A contract with no stated error is an incomplete contract.

Each contract carries an identifier, for example `TOKEN-1`. The feature that builds each one is
named in `features.md`, and a test reads the two documents together. A contract in one document and
absent from the other fails the pipeline.

## How to read this document

Each contract says how it is verified.

A contract verified by a test is proved by a green run in the pipeline. A contract verified by the
operator is one no test can judge, such as whether a logo is good, so the operator looks at a
rendered result before the step closes. A few contracts are verified both ways.

The contracts are grouped. There are thirteen groups.

`TOKEN` is a design token and its measured value. `BRAND` is a drawn asset. `SEE` is accessibility.
`TABLE` is one table, at field level. `ENVELOPE` is the encrypted record format. `VAULT` is key
handling on the phone. `CYCLE` is the prediction arithmetic. `SCREEN` is what one screen does.
`WIRE` is one endpoint of the application programming interface. `AUTH` is the request signature.
`PAY` is the subscription. `KEEP` is a promise about her data. `SITE` is the website on myemi.app.

This document does not say what is built today. `architecture.md` says that, section by section.

## TOKEN, the design tokens

### TOKEN-1, the colour set

Verified by a test.

Input: none. The tokens are constants.

Output: eighteen named colours, with the values the design fixed.

Errors: a hex value written anywhere outside `packages/tokens` fails the lint rule and the build.

### TOKEN-2, contrast is enforced and not documented

Verified by a test.

Input: every token marked as a text colour, and the ground it is used on.

Output: a contrast ratio for each pair.

Errors: a ratio below 4.5 fails the test, and the failure names the token and the ratio. A text
token that names no ground fails, because an unmeasured colour is the thing this contract exists to
stop.

### TOKEN-3, the type scale

Verified by a test.

Input: none.

Output: six sizes, each with its line height and its face.

Errors: a size whose line height is below 1.2 times the size.

## BRAND, the drawn assets

### BRAND-1, the wordmark

Verified by the operator, who looks at the rendered mark.

Output: `emi` in lowercase Fraunces. The dot of the `i` is a ring of the stem's stroke width, with a
gap of 40 degrees that opens at the upper left.

Errors: the gap is not visible when the mark is drawn at 16 points. The step widens the gap until it
is visible, and it records the final angle.

### BRAND-2, the application icon

Verified by a test for the sizes, and by the operator for the drawing.

Input: `brand/logo/emi-icon-mark.svg`.

Output: every icon size both stores require, generated by one TypeScript program.

Errors: a size the store asks for is missing. The ring is not at 77 percent of the width. The source
is a shell script rather than TypeScript.

### BRAND-3, the ring geometry

Verified by a test.

Input: a cycle of some number of days, the current day, and the four phase boundaries.

Output: four arcs sized by their own day counts, each at least as wide as its whole name on the
ring of Today, a gap of 3 degrees of ground between neighbouring arcs, elapsed days at full strength, days ahead at 20 percent, and a pointer on the current day.

Errors: the arcs and the gaps do not total 360 degrees. A gap is absent. The pointer sits on a day
outside the cycle. A phase of zero days draws an arc rather than nothing.

### BRAND-4, the illustration refuses five subjects

Verified by the operator, who looks at each piece.

Output: abstract shapes only.

Errors: a body, a face, a flower, a droplet or blood appears in any illustration.

## SEE, accessibility

### SEE-1, the ring is readable without colour

Verified by a test.

Input: the rendered ring.

Output: a gap in the ground carries every phase boundary, and the current phase is named in words
inside the ring.

Errors: a boundary that exists only as a change of colour. A phase name that is absent.

The measurement behind this contract: simulated for deuteranopia, the period and follicular colours
both become olive, and the ovulation and luteal colours both become slate. A ring that separates its
phases by colour alone is unreadable to about one man in twelve. This contract may not be weakened.

### SEE-2, a phase fill never carries text

Verified by a test.

Output: text sits on the darker ink partner of a phase colour, never on the fill.

Errors: text of any size is drawn on the period, follicular, ovulation or luteal fill.

### SEE-3, tap targets

Verified by a test.

Output: every interactive element is at least 44 points on both axes, except a day square of a
calendar month. A day square is at least 44 points high. Its touch is the width of its column plus
half the gap on each side, so no point in the row belongs to no square.

Errors: any other element below 44 points, named with its measured size. A day square whose touch
leaves a point of its row with no square.

### SEE-4, motion respects the setting

Verified by a test.

Output: the ring animates once on open, and it stays still when the operating system asks for
reduced motion.

Errors: the ring animates while the reduced motion setting is on.

## TABLE, the tables at field level

### TABLE-1, the day log table

Verified by a test.

Output: the eight columns of the design, with their types, their nullability, and the unique
constraint on the day.

Errors: a row whose day is not written as a year, a month and a day. A second row with the same day.
A revision that does not rise on a write. A payload that is not a valid envelope. A write that
leaves the update time behind the creation time.

### TABLE-2, the cycle table is a cache and never a source

Verified by a test.

Output: the table is rebuilt from the day log whenever a period day changes.

Errors: a value in the cycle table that cannot be derived from the day log. Any attempt to sync this
table.

### TABLE-3, the sync state holds exactly one row

Verified by a test.

Output: one row, holding the account identifier, the cursor and the time of the last sync.

Errors: a second row is accepted.

### TABLE-4, the vault table

Verified by a test.

Output: the account item and the record item of the design, with the index on the update time.

Errors: an item carrying a date, a symptom, a flow or a note in any attribute. The whole product
rests on this one, so a test reads every attribute of a written item to prove it.

### TABLE-5, the profile table

Verified by a test.

Output: one table that holds at most one row, with seven columns: the identifier, the column that
holds the table to a single row, the sealed payload, the revision, the creation time, the update
time, and the revision the server has confirmed. The payload is one sealed profile record.

Errors: a second row. A revision that does not rise on a write. A revision below 1. An empty
payload. A creation time or an update time that is not written as an instant. An update time behind
the creation time. A confirmed revision above the revision. Any field of the profile written in
plain text, in this table or in any other. A row left behind after delete everything.

The record inside the payload carries the kind, the name, the year of birth, the cycle length in
days, the period length in days, the regularity, the feeling, the goals, the focus, and the time of
the write. The kind and the time of the write are required. Every other field is optional, and an
absent field is an answer she skipped. `ENVELOPE-2` refuses a value outside its range.

## ENVELOPE, the encrypted record format

### ENVELOPE-1, the format

Verified by a test.

Input: a plaintext record and a key of 32 bytes.

Output: one version byte of `0x01`, then a nonce of 24 bytes, then the ciphertext and its
authentication tag of 16 bytes.

Errors: a nonce used twice. A version byte that is not `0x01`. A truncated input. A flipped bit
anywhere, which the reader must refuse rather than decrypt.

### ENVELOPE-2, the plaintext shape

Verified by a test.

Input: the fields of the design, as canonical JSON with sorted keys and no whitespace. Two records
travel in this shape: the day record, and the profile record the first run writes. A profile record
names its kind inside the ciphertext and a day record names none, so a reader tells the two apart
after it opens them and the server cannot tell them apart at all.

Output: the same bytes every time, for the same record.

Errors: a key the shape does not name, in either record. In a day record, a temperature outside
34.0 to 42.0 degrees Celsius. A weight outside 20.0 to 400.0 kilograms. An energy outside 1 to 5. A
note longer than 2000 characters. A symptom slug that is not in the catalogue. A missing day. A
sex, a sex drive, an orgasm answer, a discharge or an ovulation popup answer that
`docs/design/data-model.md` does not list. A product, a food or a sign of ovulation that it does
not list, the same one twice, or an empty list. The answer "nothing yet" beside a sign. Signs
of ovulation without the popup answered, or the popup answered without signs. In a
profile record, a name longer than 40 characters once the spaces at each end are taken off, or a
name carrying a line break. A year of birth outside 1940 to the current year less nine. A cycle
length outside 21 to 45 days. A period length outside 1 to 15 days. A regularity, a feeling, a goal
or a focus that the design does not list. The same goal or the same focus twice. A missing kind. A
missing time of the write.

### ENVELOPE-3, fixed vectors

Verified by a test.

Input: a key, a nonce and a plaintext, all checked in.

Output: a checked in ciphertext, byte for byte.

Errors: a change to the format that the vectors do not catch. A new version byte must add vectors
rather than change them.

### ENVELOPE-4, the service cannot decrypt

Verified by a test.

Output: the vault service imports the envelope's validator and nothing else from the crypto package.
The claim handler holds a vault key for the length of one call and opens no payload with it.

Errors: the service imports a decrypt function. A vault key in a log line, an access log entry or a
table attribute. A test reads the service's own import graph.

## VAULT, key handling on the phone

### VAULT-1, the vault key

Verified by a test, and by the operator on a real device.

Input: none, at first run.

Output: 32 random bytes in the keychain, made once and never replaced.

Errors: a second creation while one exists. The key in any log, any export, any error message or any
crash report.

The operator's half: the key survives the application being deleted and installed again. That is the
platform's behaviour, and platforms change it, so it is measured on a device and not assumed.

### VAULT-2, the vault key wrapped in the cloud

Verified by a test.

Input: the vault key as 32 bytes, and the account identifier as the encryption context.

Output: the ciphertext the Amazon key service returns, written to the account item, and the same 32
bytes handed back to a phone that passes a verified claim.

Errors: the plaintext key in a log line, an access log entry or a table attribute. A decrypt by any
role but the one the claim function runs as. A decrypt whose encryption context does not name the
account the caller proved. A second role in the account that may call the key.

### VAULT-3, the lock

Verified by a test.

Output: the application asks for the device biometric on return from the background. The setting is
on by default.

Errors: any screen content is visible in the application switcher preview.

## CYCLE, the prediction arithmetic

### CYCLE-1, a cycle

Verified by a test.

Input: the day logs.

Output: a cycle starts on the first bleeding day that she did not mark unexpected, and it ends the
day before the next one.

Errors: a day she marked unexpected starts a cycle. A cycle of zero days. Two cycles that overlap.

### CYCLE-2, the forecast

Verified by a test.

Input: at least two complete cycles.

Output: a predicted start, as a range, from the median of the last six lengths and their spread.

Errors: a single date rather than a range, anywhere in the interface. A forecast from fewer than two
cycles. The mean used in place of the median.

### CYCLE-3, the learning state

Verified by a test.

Input: fewer than two complete cycles.

Output: the home screen says that Emi is still learning, and it uses the length she gave at first
run.

Errors: a confidence shown while Emi is learning.

### CYCLE-4, ovulation and the fertile window

Verified by a test.

Input: the predicted start, and a luteal length of 13 days until her temperature refines it.

Output: an estimated ovulation day, and a window from five days before it to one day after it.

Errors: any wording that a day is safe, or that a pregnancy can be prevented or achieved. A test
reads every string in the application for the forbidden wording.

### CYCLE-5, confidence bands are measured and not felt

Verified by a test.

Input: published distributions of cycle length, cited in the code.

Output: three band edges, each one traceable to its citation.

Errors: a band edge with no citation. Until this contract holds, the interface marks the bands
provisional.

### CYCLE-6, the four phases

Verified by a test.

Input: her cycle length, her period length, and the cycle day of the forecast ovulation. Until two
cycles are complete, the ovulation day is the cycle length plus one, minus the luteal length.

Output: four phases, as cycle days counted from one. The period is days 1 to the period length. The
follicular phase is the day after the period to the day before the ovulation phase, so no two
phases share a day. The ovulation phase is five days: the ovulation day, two days before it and
two days after it. The luteal phase is the day after the ovulation phase to the last day of the
cycle. On a period day the phase she is in is the period. A day past the last day is luteal until
the next period starts.

The ring draws four arcs that do not overlap: the period arc, then the follicular days after the
period, then the ovulation phase, then the luteal phase. The fertile window of CYCLE-4 is a
separate thing, and the calendar marks it, not the ovulation phase.

Errors: an ovulation phase on a period day. In a short cycle the ovulation phase starts on the day
after the period at the earliest, and it can then hold fewer than five days, or none. A cycle of no
days, or a part of a day.

### AUTH-1, the signature

Verified by a test.

Input: the method, the path, an instant and the SHA-256 hash of the body, joined by newlines.

## PAY, the subscription

### PAY-1, the products

Verified by a test.

Output: one subscription group in the App Store, named `Emi`, which holds three auto renewing
products. `blue.atlantic.emi.yearly` runs for one year at 39 euros. It carries one introductory
offer of one free month. `blue.atlantic.emi.monthly` runs for one month at 5 euros, and it carries
no offer. `blue.atlantic.emi.yearly.halfprice` runs for one year at 19.50 euros, every year, and it
carries no offer. The value added tax sits inside each price, because Apple shows a price with the
tax inside it outside the United States and Canada.

The free month belongs to the yearly product alone. A subscription group gives one introductory
offer to one woman, so a second free month cannot exist.

Every product sits at level 1. Equal levels make a move between two products a crossgrade. The App
Store makes that move on her next renewal date. So she keeps the period she paid for, and the new
price starts when the old period ends. Emi refunds nothing.

The yearly product is the plan `PAY-6` sells on myemi.app. The two prices need not match.

Errors: a configuration test finds a different price, a different period, a different identifier,
or no product at all. A free month on the monthly product or on the half price product. A half
price that is not half of the yearly price. A product at a level of its own, which makes the move
an upgrade and takes the new price at once. A price written anywhere but the one module that holds
the products. A product taken off sale while a woman holds it, because Apple then refuses her
renewal and reports `PRODUCT_NOT_FOR_SALE`.

### PAY-2, the entitlement

Verified by a test.

Input: the store, on launch.

Output: whether she is subscribed.

Errors: a store that cannot be reached costs her access, rather than the last known answer being
kept. A second install asks her to pay again when the store says she owns it.

### PAY-3, the receipt is checked on the server

Verified by a test.

Input: a store transaction.

Output: the date the subscription runs to, on the account item.

Errors: a receipt accepted with no call to Apple or to Google. A receipt from one store checked
against the other.

### PAY-4, a lapse is humane

Verified by a test.

Output: reading, exporting and deleting stay open forever. Only new writes stop.

Errors: anything that makes her own history unreadable to her.

### PAY-5, the entitlement record

Verified by a test.

Output: one item in the vault table of `TABLE-4`, in a partition of its own. The partition key is
`PAY#` and the payer digest, which is 26 characters of Crockford base 32. The sort key is `META`.
`paidUntil` is an instant, and it is absent until the free month or the first payment lands.
`route` is `card` or `stars`. `state` is `active`, `cancelling`, `lapsed` or `refunded`, and
`cancelling` means she stopped the renewal while the year she paid for still runs. `payerRef` and
`subscriptionRef` are the two Stripe identifiers, and both are absent on the Stars route.
`chargeRef` is the Telegram charge identifier of the last payment, and it is absent on the card
route. `eventAt` is a number of seconds, and a write happens only when its own `eventAt` is newer
than the one on the item, because Stripe promises no order of delivery. `firstSeenAt` and
`updatedAt` are instants. An account reaches the item through `payerDigest`, one attribute on the
identity item the account already holds.

A caller asks this item one question. Is this account paid until a date? The answer is one instant
and nothing else. A screen turns that instant into words.

A delete of her account leaves this item exactly as it was, because it is the record of a sale and
it holds nothing of hers. The delete removes the link instead, so the payment stays and no account
points at it.

The store route writes its own half, on the account item of `TABLE-4`. That item is `ACC#` and the
account identifier, with the sort key `META`, and her device key makes it when the phone registers
under `WIRE-1`. Seven attributes carry the subscription, and `PAY-3` is the call that fills them.

`subscribedUntil` is a string, an instant. It is the expiry instant Apple returned. It is the one
field every reader wants.

`subscriptionStore` is a string. It is `apple`. The field exists so a second store can write its
own name later without a second shape.

`subscriptionTransaction` is a string. It is the original transaction identifier of her
subscription, which is the one identifier that survives every renewal. The server needs it to ask
Apple anything later.

`subscriptionCheckedAt` is a string, an instant. It is when the server last asked Apple.

`subscriptionState` is a string. It is `active`, `cancelling`, `lapsed` or `refunded`, which are the
four words the item above already uses. Without it a reader cannot tell a woman who stopped the
renewal from a woman who is paying, because both hold a date in the future.

`subscriptionEventAt` is a number, the seconds of the store event that last wrote these fields.
Every write is conditional on a newer value, because Apple retries a notification five times over
three days. So a retried expiry can arrive after the renewal that followed it. Without the
condition, that retry locks a paying woman out of her own diary.

`subscriptionPlan` is a string. It is one of the three product identifiers of `PAY-1`, and the plan
row in Settings reads it.

The server writes all seven from the answer Apple gave it. It writes none of them from the body the
phone sent.

Errors: an item carrying an account identifier, a record identifier, a name, an address, a card
number, a country or a Telegram user identifier. A write from an older event that moves the date
back. A query of an account partition that reaches this item. A role that can read a partition
whose key does not open with `PAY#`, or that can scan the table, which a test reads from the policy
document itself. An item removed by a delete.

Errors in the store half: a date, a state or a plan written from the body the phone sent. A write
whose `subscriptionEventAt` is not newer than the one on the item, which moves a date back. A state
outside the four words. A plan that `PAY-1` does not name. A store name that is not the store the
transaction came from. An account item carrying a price, a card number, a country or her Apple
Account.

### PAY-6, the Stripe route

Verified by a test.

Input: her identity token, and the payment method she gives Stripe on myemi.app.

Output: one product, and one price of 3900 in `eur`, recurring every year, with `tax_behavior` set
to `inclusive`. So she reads 39 euros, she pays 39 euros, and the value added tax sits inside that
amount in every country. One customer for each payer digest, and the digest is in the metadata of
the customer and of the subscription, which is the only thing of ours that reaches Stripe. The
payment method is collected first, on a SetupIntent with `usage` set to `off_session`. The
subscription is created second, with the yearly price and `trial_period_days` set to 30, so the
first month is free and Stripe takes 39 euros at the end of it. The webhook verifies the
`Stripe-Signature` header before it reads one field of the body, reads five events, and writes
`paidUntil` from `items.data[0].current_period_end`. A cancel sets `cancel_at_period_end` on the
subscription, and so does a delete of her account, so the year she paid for runs to its end and
Emi refunds nothing.

Errors: a price in another currency, at another amount, with another period, or with a
`tax_behavior` that is not `inclusive`, which Stripe refuses to change once the price exists. A
body read before its signature is verified, or accepted when the signature does not verify. A
period read from the subscription rather than from the subscription item, which reads nothing and
leaves the account looking unpaid. An older event that moves a newer date back. An event the
function does not know, answered as a failure instead of 200. The secret key in this repository, in
a manifest, in a variable of the pipeline or in the environment of a function. A card number, a
name or an address written by Emi anywhere.

### PAY-7, the Telegram Stars route

Verified by a test.

Input: a payment in Telegram Stars, made in the Emi bot.

Output: an invoice from `createInvoiceLink`, with `currency` set to `XTR`, exactly one price
component, and a `payload` that carries the payer digest and nothing else. The bot answers the pre
checkout query within 10 seconds, before it writes anything, because Telegram cancels the payment
after that. The payment arrives as `successful_payment`, and the bot reads four fields of it:
`invoice_payload` for the digest, `subscription_expiration_date` for the instant that becomes
`paidUntil`, `is_first_recurring` for whether this is the first period, and
`telegram_payment_charge_id` for `chargeRef`. It writes the item of `PAY-5`, with `route` as
`stars` and `state` as `active`. A refund moves `state` to `refunded` and `paidUntil` to the
instant of the refund.

The invoice is one payment for a year, or a subscription that renews every 30 days, which is the
only period Telegram sells. The operator chooses the shape and the number of Stars before anybody
builds this route, and both shapes write the same item.

Errors: a currency that is not `XTR`. A price of more than one component. A payload carrying
anything beyond the digest. A pre checkout query answered later than 10 seconds. A Telegram user
identifier written to the table. A subscription period that is not 2592000 seconds. A subscription
price above 10000 Stars.

### PAY-8, the entitlement read

Verified by a test.

Input: nothing beyond the signature of `AUTH-1`.

Output: one instant, which is the furthest date this account is paid until. The read takes
`payerDigest` from each identity item of the account, reads the `PAY#` item each one names, and
keeps the furthest `paidUntil` of them. It keeps the account item's own `subscribedUntil` as well,
so a payment in a store and a payment on the site answer through one route. The number of reads is
capped, because the number of ways in is capped.

The account item's own date is the store half of this read, and the furthest date wins. A woman who
paid in the App Store reads her date. A woman who paid on myemi.app reads hers. A woman who paid in
both places reads the later of the two, and Emi refunds neither payment.

A read whose `subscriptionCheckedAt` is older than six hours asks Apple for the subscription status
first. It writes the answer back before it replies. Six hours is a guess. The measurement that
replaces it is the number of reads for each account each day, once the product has users. Apple
limits the rate of each endpoint and answers 429 with a `Retry-After` header, so the window exists
to stay well under that limit.

The reply names one instant. It names no route, no store, no plan and no price, so a caller cannot
tell which of the two routes paid.

Errors: a reply carrying a route, a price, a payment method, a Stripe identifier or anything else
about the payment, because the caller asked one question. A payment made against a way in this
account has not linked, answered as paid. A read refused because the date passed, which `PAY-4`
and `WIRE-5` keep open.

Errors in the store half: a reply that names the store, the plan or the product she bought. A read
that keeps the site date while the store date is further, or the store date while the site date is
further. A read older than the window answered without asking Apple. A read that asks Apple on
every call, which spends the rate limit and tells the caller nothing new.

### PAY-9, the pointer that gives one purchase to one vault

Verified by a test.

Input: the original transaction identifier of a purchase in the App Store.

Output: one item in the vault table of `TABLE-4`, in a partition of its own. The partition key is
`STORE#` and the digest of that identifier. The sort key is `META`. It holds one attribute,
`accountId`. The server writes it once, with the condition that the partition key does not exist
already, so the first account to file a purchase keeps it.

The item earns its place twice.

A notification from Apple arrives with no application running. It names a transaction and it never
names an account, so this item is the only way the server finds the vault to write.

The condition is the rule one purchase pays for one vault. A second account filing the same
original transaction meets the condition and is refused. `docs/design/accounts.md` states that rule
as "One receipt pays for one vault", and this item is what makes it a conditional write rather than
a search.

The cost is named rather than hidden. This is the one record in the payment path that holds an
account identifier. So it sits in a partition of its own, and the role that writes it reaches that
prefix and nothing else. It holds no date, no price, no plan and no record identifier. A delete of
her account removes it with everything else. A reader who holds that partition learns that some
account bought something, and reads no day of anybody's history.

Errors: a second account that files the same original transaction and is allowed to. A refusal the
application shows as a fault, where the screen must say that the subscription belongs to another
Emi account. A write that reads the item first and then puts it, because two calls leave a
gap two phones can pass through. An item carrying a date, a price, a plan, a store transaction, a
record identifier or anything of hers. A query of an account partition that reaches this item. A
role that can read a partition whose key does not open with `STORE#`, or that can scan the table,
which a test reads from the policy document itself. An item left behind by a delete.

## SITE, the website

### SITE-1, the domain

Verified by a test.

Output: `https://myemi.app` answers with a certificate from Amazon Web Services Certificate
Manager, for `myemi.app` and for `www.myemi.app`. `www.myemi.app` answers 301 to
`https://myemi.app`, with the same path. A request over http answers 301 to https.

Errors: content served over http. A certificate for another name. A hosted zone that Terraform
creates or destroys, because the registration of the domain owns the zone.

### SITE-2, the origins

Verified by a test.

Output: two origins. One private bucket in Amazon S3, in eu-central-1, for the static assets, and
one Amazon Web Services Lambda server function, reachable only through a function url whose
authentication type is `AWS_IAM`. Only the Amazon CloudFront distribution reads the bucket and calls
the function, each through origin access control.

Errors: public access on the bucket. The website endpoint of the bucket turned on. A function url
with no authentication. Any principal other than the distribution allowed to read the bucket or call
the function.

### SITE-3, the languages

Verified by a test.

Output: `/en/`, `/ru/` and `/es/` each serve a home page. `/` answers 301 to `/en/`. An address
that does not exist answers 404 with an Emi page.

Errors: a page that one language has and another language does not. A page that says Emi is
something it is not. Emi is not a contraceptive. Emi is not a medical device.

### SITE-4, the pages

Verified by a test.

Output: pages rendered by a Next.js App Router application on Amazon Web Services Lambda, built by
OpenNext. The components come from shadcn, written in React JSX, and every colour, face, size, gap
and corner comes from `packages/tokens`. The site serves its own fonts.

Errors: a colour or a font that is not a token. A request from a page to any host other than
myemi.app. A cookie. An analytics script or an advertising script. Next.js telemetry turned on in
the build.

### SITE-5, the deploy

Verified by a test.

Output: a merge into `main` that changes the site builds it with OpenNext, updates the code of the
server function, uploads the assets to the bucket, clears the cache of the distribution, and checks
the live site.

Errors: an upload or a code update from a pull request, and an upload or a code update from a
machine. A password, a key or a token written into the repository.

### SITE-6, the headers

Verified by a test.

Output: every response carries six headers. `Strict-Transport-Security` for two years, with every
subdomain. A `Content-Security-Policy`. `X-Content-Type-Options` of nosniff. `X-Frame-Options` of
DENY. `Referrer-Policy` of strict-origin-when-cross-origin. A `Permissions-Policy` that hands out
neither the camera, nor the microphone, nor her location.

The content policy of a page comes from the function that draws it, and carries a nonce of 128 bits
made for that one response. The policy names that nonce for a script and for a style, and allows
nothing else inline, so the scripts Next.js writes into the markup run and a script written in by
anybody else does not. A nonce is spent when its response is: the next page gets another one. Every
other response, which is every file from the bucket, carries the policy of the edge: the origin of
the site, and no frame. The edge sets the other five headers over whatever the origin answered, and
keeps the content policy the function sent.

Errors: a response that is missing one of the six. A page whose policy carries no nonce, or carries
the nonce of another response. A policy allowing an inline script on its own account. A style
written on an element of a page, which no nonce can cover.
